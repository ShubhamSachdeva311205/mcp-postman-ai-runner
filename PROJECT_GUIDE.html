2. Postman basics (just what you need)

Postman is a popular tool for testing APIs. A few terms your manager might mention:

TermWhat it means
Request A single call to an API — e.g. GET https://api.site.com/users. It has a method (GET / POST / …), a URL, headers, and sometimes a body.
Response What the server sends back: a status code (200 = OK, 404 = not found, 500 = server error), headers, and a body (usually JSON).
Collection A saved group of requests bundled into one file (a .json file in "Postman v2.1" format). Think of it as a test suite for an API. This is the file our tool takes as input.
Variables Placeholders like {{base_url}} or {{token}} written inside requests, so you don't hardcode values. Our runner fills these in before sending.
Newman Postman's official command-line runner (needs Node.js). The old version of our project used it; the new one replaced it — see section 7.
Key point: our project does not need the Postman app open. It just reads the exported collection .json file and runs the requests itself.

3. What this project does

For every request in a collection it produces a verdict using two layers of judgement, and the worse of the two wins:

Layer 1 — Deterministic checks

Always run. 100% reliable. No AI needed.

  • Status ≥ 500 → FAIL
  • Status ≥ 400 → FAIL
  • Response slower than 2000ms → WARN
  • Connection/transport error → FAIL

Layer 2 — AI verdict

The nuance a rule can't catch.

  • Leaked secrets / API keys in the body
  • Stack traces or error messages
  • Missing or contradictory fields
  • Malformed payloads, security smells
  • A one-line plain-English summary
Why two layers? Even if the AI is turned off or unavailable, you still get a useful, reliable report from Layer 1. The AI only ever adds insight — it can't break the basics.

4. How it works (the engine)

The whole project is built around one small shared core (in backend/core/). Three files:

FileJob
runner.py A native Python collection runner. Parses the collection JSON, fills in {{variables}}, sends each request with the httpx library, and records what came back. Capped at 50 requests for safety. It deliberately does not run Postman's own test scripts — the AI does the testing.
analyze.py The orchestrator. Runs the collection, applies the deterministic checks, asks the AI for a verdict (up to 4 requests analyzed in parallel for speed), merges the two, and builds the summary (totals, pass/fail counts, average latency).
llm.py The pluggable AI backend. Talks to three providers over plain HTTP and normalizes every answer into {status, severity, anomalies, summary}:
  • Ollama — runs locally on your machine, free, no API key (the default)
  • Gemini — Google's cloud model (needs a key)
  • Claude — Anthropic's cloud model (needs a key)
Stateless by design: nothing is ever written to a disk or database. The same core code runs identically on your laptop, inside the MCP server, and in a Docker container.

5. What is MCP — and how we built our own

What is MCP?

MCP (Model Context Protocol) is an open standard that lets AI assistants (like Claude Desktop) safely call external tools. Think of it as a USB port for AI: instead of the AI only being able to chat, MCP lets it plug into real programs and do things — run code, read files, query a database. An "MCP server" is just a program that exposes a few functions ("tools") in the shape MCP expects, and any MCP-compatible AI client can then discover and call them.

How we made this project an MCP server

We used the official mcp Python library (its FastMCP helper). Turning a normal Python function into an AI-callable tool is remarkably little code — you create a server and mark functions with a @mcp.tool() decorator. That's the whole trick. Here is the actual file (mcp_server/server.py), trimmed: 

from mcp.server.fastmcp import FastMCP
from backend.core import llm
from backend.core.analyze import analyze_collection

mcp = FastMCP("Postman AI Runner")      # 1. create the server

@mcp.tool()                              # 2. expose a function as a tool
def list_llm_providers() -> str:
    """List available LLM providers and models."""
    return json.dumps(llm.available_providers())

@mcp.tool()                              # 3. the main tool
def run_postman_collection(collection_path: str, provider="", model="",
                           use_llm=True, max_requests=50) -> str:
    """Run a Postman collection and return an AI QA report."""
    collection = json.loads(Path(collection_path).read_text())
    report = analyze_collection(collection, provider or None, ...)
    return json.dumps(report)

if __name__ == "__main__":
    mcp.run()                            # 4. start listening

Notice the two important design choices:

  • The MCP server reuses the exact same core (analyze_collection) as the website and the API. We didn't duplicate any logic — MCP is just a thin wrapper.
  • The function's docstring becomes the tool's description. That's how the AI knows what the tool does and what arguments to pass. Good docstrings = the AI uses the tool correctly.

How it's actually used

You register the server once in your MCP client's config (e.g. Claude Desktop's claude_desktop_config.json), pointing it at this file:

{
  "mcpServers": {
    "postman-ai-runner": {
      "command": "/ABS/PATH/backend/.venv/bin/python",
      "args": ["-m", "mcp_server.server"],
      "cwd": "/ABS/PATH/mcp-postman-ai-runner"
    }
  }
}

After that, you can simply tell the AI in plain English:

"Run the Postman collection at /path/to/collection.json and analyze it."

The AI recognizes it has a matching tool (run_postman_collection), calls it with the right path, and reads back the report — all without you touching a terminal.

8. Old prototype vs this rebuild

The folder MCPPostman/mcp-postman-analyzer is the original prototype. This project is a ground-up rebuild of the same idea. What changed:

Old — mcp-postman-analyzerNew — mcp-postman-ai-runner
Runs collections viaNewman (needs Node.js) + temp filesNative Python + httpx, no Node, no temp files
AI providersOllama only, one hardcoded modelPluggable: Ollama / Gemini / Claude, pick per run
InterfacesMCP server onlyMCP server + web dashboard + REST API
Safety checksNone — fully trusts the AIDeterministic checks always run; AI is a bonus
User interfaceNoneReact + Tailwind dashboard
DeploymentLocal onlyDockerized; frontend → GitHub Pages, backend → Hugging Face
StateWrites temp filesFully stateless
One-sentence version: we took the original Newman/Node-dependent, Ollama-only, MCP-only prototype and rebuilt it as a self-contained Python engine with a pluggable AI backend, deterministic safety checks, and a web dashboard — so it's portable, hostable, and works with or without an LLM.

9. How to start it

Prerequisite (for local AI): Ollama

The default AI runs locally through Ollama. Make sure it's running (ollama serve) with at least one model pulled. The app auto-detects it and picks the first installed model — no API key needed.

Step 1 — Backend (Python 3.10+)

cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cd .. && uvicorn backend.main:app --reload --port 8000

The API is now live at http://localhost:8000. Check it with http://localhost:8000/api/info.

Step 2 — Frontend (the dashboard)

cd frontend && npm install && npm run dev

Open http://localhost:5173 in your browser.

Step 3 (optional) — Run as an MCP server

python -m mcp_server.server

…or register it in Claude Desktop using the config shown in section 5.

Optional configuration (environment variables)

MCP_PROVIDER
Default provider: ollama / gemini / claude
OLLAMA_MODEL
Force a specific Ollama model (else the first installed one)
GEMINI_API_KEY
Enables the Gemini provider
ANTHROPIC_API_KEY
Enables the Claude provider

Run the tests

source backend/.venv/bin/activate && python -m pytest backend/tests -q
Demo tip: the backend (port 8000) must be started before the dashboard can run anything. If your machine has qwen3.5 or gemma pulled in Ollama instead of llama3.1, that's fine — the app just uses whichever model is installed.
